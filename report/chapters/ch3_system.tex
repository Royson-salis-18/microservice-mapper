\section{Problem Formulation}
A system is a set $S$ of $N$ services with a directed call graph. An edge $u \to v$ means that $u$ calls $v$, so a failure travels \emph{against} the arrow, from $v$ to the callers that wait on it. Every $\Delta = 5$\,s the collector produces, for each service $s$, a reading
\[
x_s(t) \in (\mathbb{R} \cup \{\varnothing\})^{8},
\]
holding CPU, memory, CPU throttling, network in and out, request rate, error share and 95th-percentile latency. The symbol $\varnothing$ marks a metric that was not reported. It is never replaced by zero, because a stopped container must be distinguishable from an idle one. Each reading comes with a container state (running, paused, restarting, exited, detached).

At time $t$ the pipeline must decide four things, using only readings up to $t$:
\begin{enumerate}[label=(\roman*)]
\item whether an incident is in progress;
\item which service is its root cause $r$;
\item which currently healthy services will be affected before the incident ends;
\item what kind of fault it is.
\end{enumerate}
The pipeline must do this without labelled failures, without changing any application, and fast enough that a decision window finishes well inside the 5\,s collection period.

\section{Proposed Solution}
The proposed system is an \emph{agent-assisted} pipeline in a concrete sense. A \textbf{collector agent} observes the containers from outside the application. A \textbf{diagnosis assistant} turns those observations into a cause, a forecast of what fails next, a fault type, a runbook and an explanation the operator can check. The evidence-weighted dependency graph sits between them. Figure~\ref{fig:arch} shows the whole system and Figure~\ref{fig:poll} one 5-second cycle.

The solution has seven steps, each described in Chapter~\ref{ch:method}:
\begin{enumerate}
\item \textbf{Observe.} Read container state, statistics and socket tables over SSH. Install nothing on the host.
\item \textbf{Build the graph.} Merge declared dependencies (from the Compose file) with observed ones, orient each socket by its listening port, and give each edge a confidence and a dependency share.
\item \textbf{Learn directions.} Where the port heuristic cannot say who calls whom, vote over dynamic and structural signals.
\item \textbf{Detect.} Judge each service against what the current load predicts for it, using its own recent past, with a robust rule layer beside the model. Treat container facts as evidence.
\item \textbf{Rank.} Split each service's deviation into what its callees explain and what they do not; run a personalised random walk over the call graph; put facts first.
\item \textbf{Predict.} Spread risk over the graph by noisy-OR with edge probabilities learned from the system's own incidents; warn early about gradual faults.
\item \textbf{Diagnose and explain.} Classify the fault type, attach a short runbook and show the evidence behind every number.
\end{enumerate}

\section{System Architecture}
The architecture has five layers (Figure~\ref{fig:arch}).

\textbf{Dashboard.} A React~19 application built with Vite. It never polls: the server pushes graph and incident updates over a WebSocket, and REST calls fetch history and configuration. Section~\ref{sec:prototype} describes the views.

\textbf{Server.} A Node.js process (Express~5, TypeScript) that owns all state and is the only component that writes to disk. The \texttt{GraphStore} holds nodes, edges and targets, the \texttt{MetricStore} a ring buffer of readings per service, and the \texttt{TraceStore} the connection events. The \texttt{IncidentManager} drives the engines and turns their verdicts into incidents.

\textbf{Connection and collection.} A connection manager keeps one SSH session per target and runs commands from a fixed catalogue (\code{docker ps}, \code{inspect}, \code{stats}, \code{logs}, and reads of \code{/proc/<pid>/net/tcp}). Reading the socket table through the container's process id works for every image, even one with no shell. An optional standalone collector can run on a host and push to the same ingest endpoint.

\textbf{Target workloads.} Unmodified Docker Compose applications.

\textbf{Test tools.} A traffic generator with per-application workflows and profiles, and a fault injector that works on containers (kill, pause, resource limits, network detach) and writes its ledger to a file the detector never reads.

The server listens on port 3001 (HTTP and WebSocket), the dashboard on 5173 and the traffic generator on 4400. The server reaches each host over SSH on port 22, and the traffic generator reaches the application's front end, typically on port 8080.

\subsection{Three engines on the same readings}
The dashboard offers three positions: Rules, Hybrid and ML. Only the active engine decides the incident, but every cycle computes all three from the same readings and graph (Figure~\ref{fig:parallel}). That has two payoffs. Switching engines never restarts the learned detector from nothing, and the Detection engines page can show what each engine detected, computed and predicted at the same moment.

\section{Scope and Constraints}
\textbf{In scope.} Docker-based services on Linux hosts reachable over SSH; container-level metrics, socket tables and logs; unsupervised detection; ranking; cascade prediction; fault typing; a dashboard; a reproducible evaluation.

\textbf{Out of scope.} Distributed tracing (the ``Traces'' page shows sampled TCP connection snapshots, not requests); application payloads; Kubernetes clusters (not tested); a language-model agent (discussed as future work); training on labelled data.

\textbf{Constraints that shape the design.}
\begin{itemize}
\item \emph{Coarse signals.} Observing from outside yields eight metrics per service every 5\,s. A brownout on an almost idle service moves none of them enough to alarm, and Chapter~\ref{ch:results} reports it as an open problem.
\item \emph{Two views of each socket.} Both ends see every connection, so direction must be recovered; otherwise every dependency looks like a cycle.
\item \emph{Slow answers from loaded hosts.} Command timeouts allow for a host under heavy load. A host that cannot answer \code{docker ps} at all shows nothing; Section~\ref{sec:hostfindings} gives a measured example.
\item \emph{One write.} The collection path only reads. The single write the mapper makes on a host restarts a container that exited with a non-zero code, with a few attempts per container at most, and \texttt{MAPPER\_AUTO\_RESTART=off} disables it. It never restarts load generators.
\end{itemize}
