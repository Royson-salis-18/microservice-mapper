\section{Module-wise Implementation}

\subsection{Connection and collection}
The connection manager keeps one SSH session per target and runs commands from a fixed catalogue. The catalogue is a list of command builders; every argument that reaches a shell is sanitised (container identifiers must match the shapes Docker itself produces, timestamps and tail lengths are validated). Timeouts are sized for a loaded host: on a swap-thrashing 2\,GB machine with eighteen JVM services, \code{docker ps} was measured at 45 seconds, and a timeout shorter than that does not degrade gracefully, it makes the whole target disappear from the graph.

Each cycle the collector asks for the container list, inspects containers it has not seen, reads statistics, and reads each container's socket table. Reading the table through the container's process id on the host (Listing~\ref{lst:hosttcp}) works for every image, including images with no shell, which had silently hidden the front end of one benchmark for weeks before it was changed. The same command returns the interface byte counters, which are exact, where \code{docker stats} prints values rounded to three significant figures.

\lstinputlisting[language=TS,caption={Reading a container's socket table and interface counters from the host (RemoteCommand.ts).},label={lst:hosttcp}]{listings/hosttcp.ts}

\subsection{Edge direction, weights and the graph}
Every connection appears in the socket tables of both ends. Recording ``scanned container calls peer'' on both sides produced a reverse duplicate for every real link, so the graph was effectively undirected: it put a cycle on every pair, which made ``downstream of X'' reach almost the whole graph and made blast radius and criticality saturate. Direction is now recovered from listening ports: whichever end owns the listening port is the callee (Listing~\ref{lst:orient}). The ephemeral port range is a fallback when a container's listen table could not be read, and when neither settles it the edge is marked unresolved instead of being given a coin flip dressed as a measurement.

\lstinputlisting[language=TS,caption={Which end of a TCP connection made the call (MetricCollector.ts).},label={lst:orient}]{listings/orient.ts}

Observed and declared edges are merged, and an observed edge expires ten minutes after it was last seen. A connection that is seen only as a recently closed socket (TIME\_WAIT, which lingers about a minute) is counted once by its connection key, so a burst of short calls does not look like many links. A call made through the host's address to a port that one service publishes is attributed to that service (a connection to a private or bridge-gateway address on a published port).

\subsection{Incidents}
The incident manager, once per target per cycle, runs the three engines' shared step, builds the evidence for the active engine, calls the root-cause engine, and either updates the open incident or opens a new one. A new incident takes the status \texttt{DEGRADED} or \texttt{INCIDENT} according to whether any service is critical (Figure~\ref{fig:states}); it is resolved when the alarm clears. Severity is raised when more than a configured number of services are critical, and lowered for a service that nothing depends on and that depends on nothing, which has no blast radius.

\subsection{Traffic generation}
The traffic controller starts and stops load through the traffic generator's HTTP API. Each application has a workflow file (a set of weighted user journeys with think times) and a set of profiles (baseline, moderate, heavy, stress, ramp) that fix the number of virtual users and their pace. An application that has no file of its own gets a generic front-page workflow (Listing~\ref{lst:modulefor}); before that change the server refused every project outside five named ones with ``no workflow defined'', which made benchmark hosts such as \texttt{bench1} undrivable.

\section{Algorithms}
Algorithm~\ref{alg:window} is one decision window. Algorithms~\ref{alg:orient}, \ref{alg:cascade} and \ref{alg:parallel} give the observation, learning and parallel-engine steps.

\begin{algorithm}[!htbp]
\caption{One decision window of the diagnosis assistant}
\label{alg:window}
\begin{algorithmic}[1]
\Require readings $x_s(t)$, container states, graph $G$ with learned directions
\Ensure alarm, ranked causes, likely-next set, fault type, runbook
\State \textbf{facts}: mark each service stopped, paused, restarting, detached or crash-looping
\State \textbf{score}: model levels $\lambda_s$ (own and symptom), rule scores $\rho_s$, anomalies $a_s$
\State \textbf{alarm}: apply the hybrid rule; if no alarm, update the propagation counts and stop
\State \textbf{rank}: services with a fact first, then by the walk share $\pi_s$ over $G$
\State \textbf{explain}: report own versus symptom evidence and what the neighbours explain
\State \textbf{predict}: $P(c)$ by Eq.~\eqref{eq:noisyor} from the top suspect; early-warning flags
\State \textbf{diagnose}: classify the fault type of the top suspect; attach its runbook
\State update $\hat p(c \leftarrow x)$ from services that newly turned abnormal
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[!htbp]
\caption{Orienting the sockets of one container}
\label{alg:orient}
\begin{algorithmic}[1]
\Require socket table of container $a$, listening ports of every container, IP-to-service map
\Ensure directed edges with direction evidence
\For{each socket row in state ESTABLISHED or TIME\_WAIT}
  \State find peer $b$ from the remote address; if unknown, test the published-port rule
  \If{the peer owns the remote port as a listening port and $a$ does not own the local port}
    \State edge $a \to b$, evidence \emph{listen-port}
  \ElsIf{$a$ owns the local port and the peer does not own the remote port}
    \State edge $b \to a$, evidence \emph{listen-port}
  \ElsIf{exactly one port lies in the ephemeral range}
    \State the side with the ephemeral port is the caller, evidence \emph{ephemeral-port}
  \Else
    \State edge $a \to b$, evidence \emph{unresolved}
  \EndIf
  \State count the connection once by its key (caller ip:port $>$ callee ip:port)
\EndFor
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[!htbp]
\caption{Learning propagation and predicting the next services}
\label{alg:cascade}
\begin{algorithmic}[1]
\Require set of services newly abnormal $O$, set of abnormal services $A$, call graph
\Ensure edge probabilities $\hat p$; risk $P(c)$ for healthy services
\For{each open trial $(c, x)$}
  \If{$c \in A$} record a success \ElsIf{the window of 12 steps ran out} record a failure \EndIf
\EndFor
\For{each $x \in O$ and each healthy caller $c$ of $x$} open the trial $(c,x)$ \EndFor
\State $\hat p(c \leftarrow x) \gets (k + m\pi_0)/(n + m)$ for every edge
\State for a suspected root $r$: $P(r) = 1$; sweep the callers upwards, $P(c) = 1 - \prod_{x \in C(c)} (1 - P(x)\hat p(c \leftarrow x))$
\State drop services that are already abnormal; report the rest above the risk cut
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[!htbp]
\caption{Computing the three engines in parallel on one cycle}
\label{alg:parallel}
\begin{algorithmic}[1]
\Require nodes, edges, new readings since the last cycle
\Ensure a verdict for Rules, ML and Hybrid; the incident for the active engine
\State step the ML engine with the new readings (load factor, residual levels, facts, walk, forecast, cascade)
\State score the same moment with the rule layer and divide by its line
\State fuse: Hybrid maximum $= \max(\text{ML level}, \text{rules}/1.25)$, facts $\to 10$; ranking by the ML order, facts first
\State for each engine record: alarm (over its line now \textbf{and} on the previous cycle), peak against its line, top five suspects
\State append the three peaks to a rolling history of 90 cycles
\State build the incident from the \emph{active} engine only
\end{algorithmic}
\end{algorithm}

\section{Security Considerations}
\label{sec:security}
The tool holds SSH access to hosts, so it was built to expose as little as it can.
\begin{itemize}
\item \textbf{Keys stay on the operator's machine.} The configuration stores only the path of the key file. Private keys are never copied into the repository, and \texttt{*.pem} files are git-ignored as a backstop.
\item \textbf{A fixed command catalogue.} Every command the server can run on a host is built by a function in one file, and every argument that reaches a shell is checked against the shapes Docker itself produces (container identifiers, timestamps, tail lengths, paths). A test checks that an identifier with shell metacharacters is refused before a command is built.
\item \textbf{Bounded output and time.} Each command has a timeout and a maximum output size, so a misbehaving host cannot make the server wait or buffer without limit.
\item \textbf{Local control surfaces.} The Fault Lab panel listens on localhost only and its requests need a header the page itself sets. Grafana and Prometheus listen on localhost and are reached through an SSH tunnel.
\item \textbf{Ingest token.} The push endpoint is protected by a token. The built-in default is for local use and must be changed when the server can be reached by others.
\item \textbf{One write on the host.} The only change the mapper makes on a host is restarting a container that exited with a non-zero code, a few attempts at most per container, never for load generators, and switched off with \texttt{MAPPER\_AUTO\_RESTART=off}.
\item \textbf{Load limits.} The traffic generator clamps the number of virtual users to a fixed ceiling and starts only from the traffic controller.
\end{itemize}

\subsection{Monitoring: Prometheus, Grafana and Loki}
Each bench carries a monitoring stack that is deliberately a \emph{separate Compose project}. The application project stays exactly what a mapper should discover, and monitoring can be started and stopped independently. The stack has Prometheus (24-hour retention), Grafana with a provisioned dashboard, Loki with Promtail shipping every container's logs, and a small exporter that reads per-container CPU, memory, network, restarts, out-of-memory kills and health from the Docker API (the same numbers as \code{docker stats}). A ``dashboard viewer'' container queries Grafana every few seconds, as a person watching the dashboard would, so those links are live and visible to a mapper. Everything listens on localhost; Grafana is reached through an SSH tunnel. Figures~\ref{fig:grafana-sf} and~\ref{fig:grafana-ll} show the provisioned dashboard of each bench: health at a glance (request rate, 5xx ratio, p95 latency, containers running, restarts, memory), request metrics from each service's own endpoint, container metrics from the Docker API, and application internals (database pool waits, unconsumed events, process memory, heap).

Grafana serves two purposes in the study. It is the operator's ordinary view of a healthy and of a faulted bench, and it is a second, independent source against which the mapper's readings can be compared on the same time axis.

\subsection{Traffic}
Each bench has an always-on, open-loop traffic generator. The default mode is \emph{organic}: visitor sessions with think times, popular products, returning users and a day-and-night wave (about twelve workers); a steady mode gives a flat load. A quiet mode stops the generator so that only a person's own clicks reach the gateway. ShopFlow also has a storefront that can be used like a customer, with a live request log and an ``autopilot'' that browses by itself.

\subsection{The Fault Lab}
The Fault Lab (\texttt{lab/faultlab} in each bench repository) is the fault injector of the evaluation. Its properties are those the methodology needs:
\begin{itemize}
\item \textbf{Blind.} The mapper is never told what is injected. Everything the injector does is written to a private ledger that is read only when scoring.
\item \textbf{Physical.} Faults act on containers: \code{SIGKILL} with the restart policy bringing the service back (crash), repeated kills (crash-loop), \code{docker stop}, pause, resource limits (brownout, memory), network detach (partition) and repeated pause-and-release cycles (flap).
\item \textbf{Organic and reproducible.} A campaign draws faults from a Poisson process with a profile, a duration, a rate, a maximum number at once and an optional seed; the same seed gives the same campaign.
\item \textbf{Targeted.} The operator may restrict the fault types and the services that may be hit, or inject one fault by hand with a severity and a hold time, and heal everything at once.
\end{itemize}
The control page (Figures~\ref{fig:faultlab-sf} and~\ref{fig:faultlab-ll}) runs on the bench host, listens on localhost only and is reached through an SSH tunnel; it starts the same commands one would type. Its requests need a header the page itself sets, so another site open in the same browser cannot drive it. The same page starts and stops the traffic, sets the average request rate and chooses its shape. The screenshots were taken of the page with no campaign running and away from the bench host, so the service list reads ``absent''; on the host each service shows its container state.

\section{Host and Mapper Diagnostic Tools}
\label{sec:tools}
Two tools were added after operating the benchmark hosts showed that ``nothing appears in the dashboard'' has two very different causes: the host cannot answer, or the mapper has a problem.

\textbf{\texttt{npm run check-host}} walks one instance step by step and stops at the first failure: whether port 22 answers; whether the key exists with permissions SSH accepts; whether login works; the host's memory, load and disk; whether docker answers within 25 seconds and which containers run; whether the application answers on its port; which peers each front-end container calls and whether they are other containers; and whether the mapper server is up. Each failure says which side to look at.

\textbf{\texttt{npm run mapper-edges}} prints what the running mapper holds for a project or service: the target's status and last-seen time, the matching nodes and their status, and every edge in or out with its evidence and last-seen time. Together the two tools separate a host problem from a mapper problem in minutes.
