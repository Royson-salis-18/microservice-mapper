5 Sensitivity

One hyperparameter changed at a time, everything else as in section 7, each point a full blocked cross-validation (the learned model is retrained and its threshold re-chosen for every point).

Sliding window of the baseline

How much recent past defines "normal" for each signal. Too short: the baseline follows a fault. Too long: it follows daily drift and old incidents.

Minimum history before a signal is judged

Signals with less past than this are not judged (cold start). Lower catches faults sooner after start-up and raises false alarms.

Persistence: consecutive moments above the threshold

An alarm needs this many moments in a row. More persistence removes one-off spikes and delays detection by one moment each.

Regularisation strength of the learned model (lambda)

Higher lambda shrinks all weights. With collinear signals a small lambda gives large opposite-sign weights that do not generalise.

Number of time blocks in the cross-validation

Stability of the estimate: results should not swing with how the run is cut.

Not swept here because they apply at collection time and the recorded data already contains their effect: the collector request-statistics window (60 s) and poll interval (5000 ms). To test them, record a new run with a different value and compare the two reports.

Paths starting with server/data are relative to the repository root when the server is started with npm run dev (the server's working directory is server/, so the folder is data/ inside it). ~/.faultlab is in your home directory on the machine that runs the injector and the observer.

How one reading travels
  1. Collect. Every 5000 ms the collector reads docker stats (CPU, memory, network counters, throttling), docker inspect (state, restarts, network attachment, CPU limit), the new log lines since the last cycle (request count, errors, latency), and /proc/net/tcp inside each container (who talks to whom). Counters become per-second rates from two readings; a counter that went backwards is unknown, not a spike.
  2. Ingest. The batch is POSTed to /api/ingest. Nodes and edges are merged into the graph, readings become one snapshot per service pushed into the metric history ring buffer.
  3. Detect. Each cycle, every signal of every service is compared with that service's own recent past (robust z, log scale for rates, one-sided). The newest 2 samples must agree. Container facts (stopped, paused, restarting, no network) are read straight from the runtime.
  4. Model. The target's own model (trained at start-up on its baseline) supplies the alarm threshold; learned weights, if installed, turn the signals into one probability per service.
  5. Rank. Root cause, cascade and at-risk list are computed from the scores and the call graph. Incidents are kept in memory and rebuilt every cycle.
  6. Serve. The React app polls /api/graph, /api/incidents and /api/models.
  7. Record and learn (offline). The observer writes what the API showed; the injector writes what it broke; npm run ml joins the two and learns.

Incident thresholds (editable in the UI; server/rca/thresholds.ts)

NameDefaultMeaning
minHistorySamples12How many past samples a service needs before it is judged at all. Below this it is skipped rather than guessed at, so a service that just started does not alert on its first reading.
zScoreAnomaly3.5How far from its own recent baseline a metric must move to count as anomalous, in noise-normalised standard deviations (a healthy series' normal extreme is about 3). Lower fires more often.
zScoreHigh5Deviation at or above this is HIGH rather than MEDIUM.
zScoreCritical8Deviation at or above this is CRITICAL.
minDeltaPercent5Even a large z-score is ignored unless the metric moved this many percentage points from its baseline. Stops an idle service going from 0.05% to 2% CPU from raising an incident.
absoluteHighPercent70A CPU or memory reading above this is HIGH no matter how calm the baseline is — a service pinned at 75% is worth seeing even if it has been there long enough to look normal.
absoluteCriticalPercent85A reading above this is CRITICAL regardless of deviation.
flatlineStdDev0.001Below this standard deviation the baseline counts as flat. Dividing by a near-zero deviation makes z-scores explode, so the flat case is judged on absolute movement instead.
flatlineDeltaPercent30On a flat baseline, how many points a metric must jump to be anomalous. This is the rule that catches an idle service suddenly doing work.
flatlineCriticalPercent80On a flat baseline, a value above this is CRITICAL rather than HIGH.
criticalServicesForCritical2How many services must be critical at once before the whole incident is CRITICAL rather than HIGH.
silenceSamples3A service that is normally busy (CPU or network) and shows no activity at all for this many samples in a row is treated as frozen. This is how a hung service is caught: it sends no errors, it just goes quiet.
monitoringGapShare0.8If at least this share of a target's services go silent or vanish at the same moment, the mapper reports a monitoring outage (collector or SSH problem) instead of blaming services.
explainAwayGamma1How strongly a broken dependency explains its callers' errors and slowness. 1 = fully; 0 = ignore the call graph and rank by how abnormal each service is.
cascadeEdgeProbability0.5Assumed chance that a failure spreads across one call edge, used for the "at risk next" list. It ranks who to watch; it is not a calibrated probability.
